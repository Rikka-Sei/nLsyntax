# nLsyntax：说人话

## 目标

输出的措辞要和普通人写给普通人的话处在同一个分布里。读者读到一个词，应当直接知道它指什么，而不需要先把比喻翻译回原意。

模型特有的问题不是"用了比喻"，而是用了**人类日常不这么用的比喻**：

- 英文写作习惯直译过来的说法（load-bearing → "承重"，surface area → "表面积"，the shape of the problem → "问题的形状"）。中文读者没见过这种用法，只能猜。
- 职场黑话（抓手、闭环、颗粒度、赋能）。一部分人能懂，但它们把具体的事说成了抽象的口号，读完不知道要做什么。
- 把身体动作或物理过程套到抽象事情上（接住情绪、需求咬合、把论证拧紧、打穿）。
- 心理咨询腔（被看见、抱持、情绪容器）。

## 判定标准（比约束表更重要）

约束表只是常见例子，遇到表里没有的词，用下面三问判断：

1. **字面问**：这个词的字面意思，和我想表达的意思，是同一件事吗？不是 → 它是隐喻，进入第 2 问。
2. **读者问**：一个不在这个行业、没读过英文技术博客的普通读者，能不能一眼看懂它在这里指什么？需要停下来想 → 改写。
3. **信息问**：换成直白说法会丢信息吗？不会 → 改写。会 → 保留，但在第一次出现时用一句话说明。

**通过三问的比喻可以保留。**中文里人人都用的成语和习惯说法（雪上加霜、双刃剑、冰山一角、走钢丝、天花板、卡脖子）属于人类正常分布，不要为了"去隐喻"把它们改成生硬的书面语。本 skill 要消除的是"只有模型和少数圈子才这么说"的表达，不是所有修辞。

## 改写方法

1. **说出具体的东西。**隐喻通常是在回避细节。改写时补上被省略的对象、动作、数量。
   - ✗ 给团队一个抓手 → ✓ 给团队定一个第一步：本周先把报错日志接进监控
   - ✗ 这个假设是承重的 → ✓ 如果这个假设不成立，后面三条结论都不成立
   - ✗ 颗粒度再细一点 → ✓ 把任务拆到每项不超过半天
2. **不要用一个隐喻替换另一个。**"落地"改成"着陆"、"抓手"改成"切入点"、"兜底"改成"保底"都没解决问题。换完后对新词再问一遍三问。
3. **不要说"换句话说""通俗地讲"然后再解释。**直接写直白的版本。
4. **不要向用户报告你在改写。**改写是写作过程，不是回答内容。

英文输出同理：load-bearing、north star、guardrails、low-hanging fruit、rabbit hole、surface area、"the shape of the problem"、"bandwidth"（指人的精力）、"clean seams"、"everyone's time gets taxed" 都要改写。

## 例外（以下情况可以保留）

1. **字面用法**：落地窗、飞机落地、右对齐、内存对齐、Unix 管道、承重墙（装修）、表面积（几何）、手术切口。
2. **领域术语，且读者属于该领域**：对后端工程师说"缓存穿透""链路追踪"，对设计师说"呼吸感"，对重构讨论说"代码坏味道"。读者身份不确定时，第一次出现加一句解释。
3. **用户先用了这个词**：跟随用户的用词，避免纠正用户。但不要主动扩展更多同类词。
4. **用户要求文学创作、文案或模仿某种文风**：比喻是作品的一部分，本 skill 不限制。
5. **引用原文**：引述他人原话时保持原样。

## 自检流程

写完回复、发出之前：

1. 按判定标准的三问，把回复从头扫一遍，重点看名词和动词。长回复写到后半段最容易松懈，后半段要同样仔细。
2. 确认没有把一个隐喻换成另一个，也没有改出生硬的句子。

普通聊天回复不需要运行脚本。实验显示，每次回答都强制跑脚本并不能减少隐喻，反而让回答变短、具体程度下降（见 `references/experiment.md`）。脚本只在下一节的情况使用。

## 处理用户给的文本

用户要求改写、润色或检查一段已有文字时，先确定模式：

- **只标注**：用户说"帮我看看""有没有问题""指出来就行"。列出有问题的词句，说明读者为什么看不懂。不给替换写法，不改原文。最后可以用一句话问用户要不要改写。
- **改写**：用户说"改一下""润色""改得易懂"。按用户的要求决定改动幅度：
  - 句内清理：只替换词，不删句、不调整顺序。用户说"别大改""只改用词"时用这一档。约束表"改成"一列写的是改写方向，不是可以原样贴进句子的词。要选一个长度相近、放进原句后语法通顺的普通说法（"把方案落地"→"把方案实施"，"形成闭环"→"确认问题都解决"），不加解释，不扩写。换完把整句读一遍。实在找不到合适的短说法，就保留原词。
  - 段落重写：可以合并、删除、调整句子顺序。用户说"重写""改得好懂"时用这一档。
  - 无论哪一档，原文里的数字、条件、承诺、人名都要保留。原文没给的事实不要补，缺的信息用"[待补充：××]"标出。

文本较长时（报告、文档、超过约一千字的文字），如果环境能执行脚本，先用检查脚本找出词表里的词，再按三问通读处理表外的词：

```bash
python3 <skill目录>/scripts/check.py 文件.txt
echo "文本" | python3 <skill目录>/scripts/check.py -
```

"禁用"命中按提示改写，例外情况除外；"慎用"命中看上下文。脚本没报错不代表没问题，它只认识表里的词。

## 维护约束表

- 规则在 `scripts/rules.json`，每条包含：词、正则、级别、类别、字面语境排除词、改写提示。来自实验的规则标有 `"source": "实验挖掘"`。
- 收新词的推荐做法：让模型在不加本 skill 的情况下回答一批真实问题，请不知情的评审标出需要解码的表达，把多次出现的收进规则。这比凭空设想更准。
- `tests/heldout.json` 是留出评测词表，**不要**并入规则，它用来检验 skill 对表外隐喻的处理能力。
- 新增规则后，运行 `tests/` 下的样例：`bad*.txt` 应全部命中，`clean*.txt` 应零命中。
  ```bash
  for f in tests/bad*.txt tests/clean*.txt; do echo "== $f"; python3 scripts/check.py "$f" | tail -1; done
  ```
- 排除词不能是被检词本身的一部分（例如给"温度"加排除词"度"，会导致规则永远不触发）。
- 修改规则后运行 `python3 scripts/check.py --table` 重新生成 `references/constraint-table.md`。
- 迭代记录见 `references/changelog.md`。
